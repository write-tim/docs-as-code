Consistency is the key to a world-class user experience. To maintain a clean, scannable, and accessible interface, all authors must adhere to these structural standards when incorporating UI components and technical formatting.

---

## The Aside Component

The [`<Aside>`](/components/asides/) component draws the reader's attention to critical information without breaking paragraph flow. **Rule of thumb: If a page has more than three asides, the core text needs to be rewritten into the main narrative.**

*   **Note (Purple):** General supplementary information, background context, or non-blocking trivia.
*   **Tip (Green):** Workflow shortcuts, best practices, or optional efficiency enhancements.
*   **Caution (Yellow):** Potential edge cases, minor data loss, or tricky prerequisites where mistakes commonly happen.
*   **Danger (Red):** Irreversible, destructive actions strictly impacting system stability (e.g., deleting a database or destroying an API token).

<Aside type="danger">
Never use a Danger aside for stylistic emphasis or simple advice. It is strictly reserved for critical warnings that prevent severe outages or permanent data loss.
</Aside>

## Procedural Steps & Tabs

When guiding users through multi-step workflows or alternative options:

*   **Procedural Steps ([`<Steps>`](/components/steps/)):** Use steps for sequential tasks where the reader must follow an exact chronological order. Each step should begin with an active imperative verb (*Click*, *Navigate*, *Configure*).
*   **Alternative Tabs ([`<Tabs>`](/components/tabs/)):** Use tabs to present mutually exclusive paths (such as macOS vs. Windows or npm vs. pnpm). Never place linear sequences inside separate tabs.

---

## Cards, Badges & File Trees

*   **Visual Link Cards ([`<LinkCard>`](/components/cards/)):** Highly recommended at the bottom of procedural articles under a "Next Steps" or "Related Reading" heading to guide reader navigation.
*   **Status Badges ([`<Badge>`](/components/badges/)):** Use sparingly within running body text. They are most effective when placed inside tables, component headers, or sidebar summaries.
*   **Directory Trees ([`<FileTree>`](/components/file-trees/)):** Prune irrelevant directories (like `node_modules/` or `.git/`) to focus the diagram strictly on the files the reader needs to touch.

## Code Formatting

Technical documentation frequently mixes plain English with code syntax. Choose the appropriate format for the context:

### Inline Code
Use single backticks (`` `code` ``) for file names (`package.json`), environment variables (`GITHUB_TOKEN`), CLI flags (`--verbose`), or UI button labels within a sentence.

### Fenced Code Blocks
Use triple backticks for multi-line scripts or terminal commands. Always specify the language identifier for syntax highlighting. Explore all styling options in [Expressive Code](/components/expressive-code/).

## Image & Media Guidelines

Images should clarify complex UI interactions, not replace well-written prose.

1.  **Keep it Focused:** Crop screenshots tightly to the relevant UI dialog or button. Avoid full 4K desktop captures.
2.  **File Formats:** Use `.png` for crisp UI screenshots and `.webp` or `.jpg` for larger, complex images. Astro compresses and converts images to WebP automatically.
3.  **No Text in Images:** Never embed critical instructions directly inside an image graphic. Screen readers cannot parse it, and it cannot be easily translated.
4.  **Always Add Alt Text:** Screen readers and search indexers require descriptive alternative text for every uploaded graphic.

> 🖼️ **Media Walkthrough:** Learn how to upload assets and write high-value alt text in [Managing Media & Assets](/writers/media-management/).
